# Task Decomposition Scenarios V1 设计

## 状态

Accepted. 用户已确认长期目标拆解先不考虑，本轮只扩近期可落库、可验证的任务拆解场景。

## 背景

Plan 13 已经把单一考试复习计划推进到稳定闭环：缺少学习上下文时先 intake，随后 `get_free_slots -> create_study_plan -> review -> create_task`，确认后由本地确定性分支逐条写入任务。

现在需要扩的不是长期学习规划，而是更贴近日常使用的短中期场景：

1. 作业、报告、大作业、实验报告等 deadline 型任务拆解。
2. 多门考试同时存在时的复习排程。
3. 用户确认或写入后觉得计划太满、太少、时间不合适时的计划调整。
4. 时间不足或已有任务冲突时，给出可见失败和可调整路径，而不是假装全部完成。

## 目标

1. 作业/报告/大作业请求能先补齐交付物、要求、工作量、每日上限等上下文，再生成 3-6 条候选任务。
2. 候选作业计划和复习计划一样，必须先 review，用户确认后再逐条 `create_task` 写入。
3. 多考试请求继续使用 `create_study_plan`，但 E2E 要覆盖同一轮里至少两门考试的复习任务写入。
4. 计划调整 V1 支持“某个近期计划太满，改成每天最多 N 小时/分钟”这类明确请求：先列出现有任务，确认后批量 `update_task` 缩短任务时长。
5. 时间不足 V1 以每日上限、空闲时段和 `create_task` 冲突失败为边界：生成器要尊重每日上限；写入失败时要明确告诉用户失败数量和原因。

## 非目标

1. 不做长期目标拆解、学期级学习路径、能力诊断或成长规划。
2. 不引入多 Agent、BERT 分类器、RAG 或新的调度框架。
3. 不重写 Agent Loop；继续复用现有 function calling 工具闭环。
4. 不把候选计划工具改成直接写库。
5. 不做复杂跨天重排、自动删除任务、任务依赖图或甘特图。

## 方案

### 1. 新增 `create_work_plan`

新增一个候选计划工具，专门处理 deadline 型工作：

- 输入 `work_items`：标题、截止日期、类型、课程名。
- 输入 `available_slots`：来自 `get_free_slots`。
- 输入 `work_context`：交付要求、评分/格式要求、已完成进度、每日最大工作时长、原始补充。
- 输出候选任务数组，不直接落库。

生成 prompt 要求：

- 任务在截止日前完成，不能安排到截止日期之后。
- 每条任务在一个空闲时段内，不能跨时段。
- 每条任务 30-120 分钟；有每日上限时，同一天总时长不超过上限。
- 节奏至少覆盖：明确要求/收集材料、提纲或方案、初稿/实现、修改完善、提交检查。
- 标题和 description 必须体现作业/报告主题与具体产物。

### 2. 作业计划本地入口

在 `run_agent_loop` 前置一个本地 shortcut：

1. 识别带截止日期的作业/报告/大作业请求。
2. 如果缺交付上下文，先发一次 `ask_user`，询问要求、格式、工作量、每日上限；用户可回复“按默认”。
3. 调用 `get_free_slots` 获取从当前日期到截止日前一天的空闲时间。
4. 调用 `create_work_plan` 生成候选任务。
5. 使用通用计划 review，用户确认后逐条 `create_task`。

这样能把高频 deadline 场景固定在可验证路径里，不依赖模型在确认后继续自由调用工具。

### 3. 通用计划 review/write

把 Plan 13 的 `_run_confirmed_study_plan_write` 泛化为通用函数：

- 接收候选任务、计划名称、确认文案、取消文案和完成文案。
- 复习计划、作业计划都复用同一个确认写入过程。
- 仍然逐条调用 `create_task`，并保留冲突失败统计。

### 4. 计划调整 V1

新增本地计划调整 shortcut，先支持明确且可控的一类：

用户表达“某个计划太满/每天最多 N 小时或 N 分钟”时：

1. 从用户话术中提取计划关键词，如“机器学习报告”“报告”“英语复习”。
2. 列出未来 30 天内匹配关键词的 pending 任务。
3. 如果没有匹配任务，返回明确提示，不乱改。
4. 如果有任务，生成 review：列出要调整的任务和新的每日上限。
5. 用户确认后，逐条 `update_task` 缩短任务结束时间，单条任务最长不超过每日上限。

V1 不做跨天搬移；如果缩短后仍不够，提示用户重新生成计划或手动给更多空闲时间。

### 5. 测试与 E2E

后端回归覆盖：

- `create_work_plan` schema 和 executor。
- `generate_work_plan` prompt 包含 `work_context` 和每日上限。
- 作业计划 shortcut：缺上下文先 ask_user，确认后写入任务。
- 计划调整 shortcut：根据关键词找到既有任务，确认后批量 `update_task`。
- 工具 schema 暴露 `create_work_plan`。

Live E2E 覆盖：

- 作业/报告计划：用户补充上下文后，写入至少 3 条阶段任务。
- 多考试复习：同一轮写入至少两门考试相关任务。
- 计划调整：对已写入的报告计划发送“太满，每天最多 1 小时”，确认后 DB 中相关任务时长不超过 60 分钟。

## 验收标准

1. Plan 14 设计和执行计划文档存在，并明确长期目标拆解为非目标。
2. `create_work_plan` 工具、执行器和生成器可用。
3. 作业计划、复习计划、多考试和计划调整都保留确认后写库。
4. 后端定向回归通过。
5. 前端 typecheck 通过。
6. 沙箱外 Agent Loop live E2E 通过新增场景，并写出 evidence JSON。
7. `progress.md` 记录本轮完成内容、验证命令和剩余边界。
